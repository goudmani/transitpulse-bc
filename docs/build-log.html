Six of those eighteen bugs were silent: every job reported success, every dashboard was green, and the data was wrong anyway. Those are the ones worth reading about. A crash tells you where it is. A silent bug tells you nothing, and the only thing standing between it and a published number is somebody deciding to check.

The route

How it got built

Nine stops, in order. Each one produced something that worked and something that didn't.

Stop 1 · Foundations

Terraform, and an API key that nearly went public

Eight Terraform modules, 151 resources, OIDC federation so GitHub Actions could deploy without long-lived credentials. Before any of that ran, the very first thing worth checking turned out to be the smallest file in the repo.

.gitignore contained one line. .env, holding the TransLink API key, was not in it. The first git push would have published a working credential to a public repository.

Stop 2 · Ingestion

GTFS-Realtime into Kinesis, twice as fast as allowed

A Lambda polls three TransLink GTFS-Realtime feeds, decodes protobuf, and writes to a Kinesis stream that Firehose drains into S3 as Parquet. Roughly 16 million rows a day.

One shard accepts 1,000 records per second. The poller was pushing about 2,400. Kinesis throttled, invocations failed, and polls went to the dead-letter queue. That loses data that can never be re-fetched, because a real-time feed has no history.

Stop 3 · The lakehouse

Bronze, silver, gold, and 25 rows collapsing into one

Bronze is raw Parquet. Silver is Iceberg, one row per arrival rather than per prediction: the feed re-publishes its guess for the same bus at the same stop every two minutes, so 2,021,771 bronze rows collapsed to 79,945 real stop events. Gold adds the point-in-time-correct features the model trains on.

The rule the gold job exists to enforce: every feature must have been knowable 15 minutes before the arrival it predicts. Historical aggregates use service dates strictly earlier than the run date. Break that and the metrics look excellent and mean nothing.

Stop 4 · Cost

$120/month, projected, on day three

The first days ran at about $4/day. The estimate had been $21/month. Four changes brought it to $0.79/day. That is a scale where a portfolio project can run for a month without thinking about it.

The largest single win was counterintuitive: Firehose bills every record rounded up to 5 KB, and the rows were about 200 bytes each. Unpacked, 2.3 GB of real data was being billed as 57 GB. Packing 100 rows into each Kinesis record fixed it, with a de-aggregation processor on the Firehose side to split them back out again.

Stop 5 · Data quality

Three per cent of the rows were buses that never came

GTFS-Realtime marks cancelled trips with schedule_relationship = 3. A cancelled trip never arrives, so its last-published delay is fiction. The field was being dropped at the bronze-to-silver boundary, so nothing downstream could filter on it.

Filtering them removed only 0.7% of stop events, because cancelled trips get re-published more often than scheduled ones, but it raised label completeness from 0.982 to 0.991.

Stop 6 · The silent ones

Eight days of collection, one day of data

Gold held exactly one service date after eight days of successful nightly runs. Every Glue job had reported SUCCEEDED with a correct row count, every day.

Spark's default partitionOverwriteMode is STATIC, which deletes the entire table path before writing rather than just the partitions being written. Every night the job wiped the previous week and wrote one day. Silver never showed it because Iceberg MERGE accumulates. The monitoring counted silver, so it cheerfully reported "8 of 21 days collected, healthy" throughout.

Stop 7 · Time

A timestamp is not a time until you say where it is

Four separate defects turned out to be one mistake wearing different clothes. The worst: hour_of_day, day_of_week and is_weekend were derived from a UTC timestamp, but the peak-hours list was written for local hours. Vancouver is UTC−7 in summer, so every arrival after 17:00 local was stamped with the next day's date. That is about 29% of rows, and the second-busiest stretch of the day. A Friday evening bus was labelled Saturday.

The fix is from_utc_timestamp(ts, "America/Vancouver"), a real zone rather than a fixed −7, because the collection window crosses the daylight-saving boundary and a fixed offset is a bug with a delayed fuse.

Stop 8 · The split

Two weeks held out, never shuffled

7.23M rows to train, 4.13M to validate, 4.16M to test, split by date and not at random. A random split leaks the future through the historical aggregates: a row from Tuesday helps predict Monday, and every metric becomes fraudulent.

The split key is the GTFS service date, not the calendar date, so a trip departing 23:40 and arriving 00:20 lands wholly on one side of the boundary instead of straddling it.

Stop 9 · The model

114.3 seconds, and a baseline that was not the one we expected

XGBoost, optimising absolute error directly because that is the metric being reported. Trained on SageMaker, evaluated against three baselines on the held-out week, gated on the result, and registered.

The surprise was which baseline was hardest. The project had assumed persistence would be the bar. The historical median beat it, and the registry gate had been pointed at the wrong one.

The interesting part

Six bugs that reported success

Ordered by how long they would have survived undetected.

Silent · found by reading row counts

Athena partition projection is an Athena feature. Spark cannot see it.

The bronze table used partition projection, which lets Athena infer partitions from a naming pattern instead of a metastore. Spark has no such concept, so the Glue job found no partitions, read zero rows, wrote zero rows, and finished in 73 seconds reporting SUCCESS.

Fix: read the S3 prefix directly instead of the catalog table. Lesson: a job that finishes suspiciously fast has not finished.

Silent · found by checking a nullable column

to_timestamp() on an epoch integer returns NULL

GTFS timestamps arrive as Unix epoch seconds. to_timestamp() parses strings. Given a bigint it returns null rather than erroring. Four temporal features were silently null for every row.

Fix: timestamp_seconds(). Lesson: in Spark, a type mismatch is usually a null, not an exception.

Silent · found by plotting the data

Temporal features in UTC, thresholds in local time

29% of rows carried the wrong hour, the wrong day of week, and the wrong weekend flag. Nothing failed. The model trained happily on it.

Found by: drawing an hour-of-day chart and noticing it showed a bus network with no overnight trough, which is not a thing that exists. Lesson: plot the data. A chart of something physical fails visibly in a way a row count never does.

Silent · found by asking "why only one folder?"

The nightly job deleted six days of work, every night

Spark's static partition overwrite mode wipes the whole table path. Eight successful runs produced one day of data. Every job was green.

Fix: partitionOverwriteMode = dynamic, then backfill. Lesson: monitor the thing you care about, not its upstream. The health check counted silver rows, so it never noticed gold was empty. A gold-partition check was added to the ops agent afterwards, reading S3 directly, because partition projection would have described folders that could exist and hidden the bug all over again.

Silent · found by reading a header

The static feed had a column the schema didn't

TransLink's trips.txt includes trip_short_name, which the generic GTFS DDL omits. Registering the table with the wrong column order would have shifted every field by one, with route_id reading from service_id, and no error at any point.

Found by: checking the header bytes of the CSV before registering the table rather than after. Lesson: a specification describes what a feed may contain, not what this feed does contain.

Silent · found by not trusting a $0 bill

Cost reporting that always said zero

The Cost Explorer API appeared to report near-zero spend. It wasn't broken: the account was covered by credits, and an unfiltered query sums Usage, Credit and Tax record types, so credits netted usage to roughly nothing.

Fix: filter RECORD_TYPE = Usage. Lesson: gross usage is the number that answers "is this wasteful". Credits run out. The burn rate is what you are actually managing.

The pattern across all six: none of them threw. Every one was found by somebody looking at an actual number and asking whether it was plausible: a row count, a column header, a chart shape, a folder listing, a bill. The tests passed throughout. The dashboards were green throughout.

Modelling

The gate was pointed at the wrong baseline

A quality gate that lets a model into the registry is only as honest as the thing it compares against.

BaselineMAEWhat it assumes
Published schedule152.1sthe timetable is right; predict zero delay
Persistence130.2sa bus four minutes late stays four minutes late
Historical median127.3sthis stop, at this hour, on this type of day
XGBoost114.3sthe model

The pipeline gated on mae_ratio_vs_persistence <= 0.92, which assumed persistence was the toughest baseline. It isn't. To rule out an artefact, since the historical feature is null for 16% of rows and falls back to predicting zero, both were re-scored on only the 3,489,305 rows where both are genuinely defined. The gap widened: 126.1s for historical against 131.5s for persistence.

So delay at a given stop is more a property of that stop at that hour than of the individual bus. Left alone, the gate would have admitted a model scoring 125s, worse than a lookup table, while reporting that it had passed. It now measures against whichever baseline actually wins.

Fifteen trees. Training was configured for 800 boosting rounds. Early stopping halted at 64, with the best validation score at round 15. Past that, training error kept falling while validation error rose. With 7.2 million training rows that is not a shortage of data. It is two different weeks of a city. Early stopping is the difference between noticing that and shipping it.

Infrastructure

Four fights with AWS

Every training quota was zero

Not just spot. Every ml.* training instance quota on a new account was 0, so turning off spot changed nothing. Two quota increases, both free. A further trap: the request API validates against the published default, not your applied value, so asking for 2 of a quota defaulting to 4 is rejected as a decrease even when you currently have none.

Two APIs that look identical

In the SageMaker SDK, estimator.fit() means "train now" under a Session and "record this step" under a PipelineSession. Using the wrong one produced a TypeError about string conversion, which was botocore crashing while formatting its own error message about an unresolved pipeline variable.

Alarms cannot cross regions

Billing metrics only exist in us-east-1, but a CloudWatch alarm can only act on an SNS topic in its own region. The cost alarm needed a second topic in us-east-1 subscribed to a cross-region forwarder.

Deleting an instance is not deleting a cluster

An orphaned Aurora cluster in an unrelated region had been quietly billing for weeks. The RDS instance had been deleted; the cluster had not. They are separate objects with separate lifecycles.

If I did it again

What I would change

Store timestamps with their zone, once

Four bugs, one root cause. The fix is not vigilance at each call site, it is making the zone part of the value so a naive local-time comparison is impossible to write.

Assert the invariant, not the run

Every silent bug passed because the job checked "did I finish" rather than "is the output the shape it must be". Row conservation across a split, partition count matching distinct dates, no nulls in a required column. Cheap assertions that fail loudly.

Plot it on day one

The timezone bug survived weeks of green dashboards and died the moment someone drew a chart. Physical data has a shape you already know. A bad chart is obvious in a way a bad row count is not.

Collect through a season change

27 days of late summer means the four weather features learned almost nothing, because there was almost no weather. The interesting variance in transit delay is in November.
