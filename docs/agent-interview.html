Rate limiting

The most common shallow answer is "add retries." The distinction that separates candidates is knowing that pacing, retrying, and budgeting are three different problems with three different solutions.

Your agent calls a rate-limited LLM API. How do you handle it?

What they're testingWhether you know that retrying and pacing are not the same control.

Three layers, and they solve different failures:

  • Pacing (proactive). Don't send faster than the budget in the first place. A token bucket smooths request arrival. Ours is InMemoryRateLimiter(requests_per_second=0.25).
  • Retry (reactive). When a 429 comes back anyway, honour Retry-After and back off exponentially with jitter. max_retries=4 on the ChatGroq client.
  • Budget (hard ceiling). A tokens-per-day quota is not a rate — it's a finite allowance. No amount of pacing saves you once it's gone; you have to degrade.
The trap

"I'd add retries with exponential backoff" alone. Under sustained overload, retries make it worse: every client retries at once, latency compounds, and you burn quota on requests that were always going to fail. Retries handle transient spikes. Pacing handles steady-state load.

RPM or TPM — which one binds first in an agent?

What they're testingWhether you understand why agent loops are expensive in a way single-shot calls are not.

Tokens per minute, almost always — and the reason is structural. An agent resends the entire conversation on every turn, including all prior tool output. Turn k costs roughly k units, so n turns cost O(n²) tokens while costing only n requests.

Groq free tierLimitWhat we actually use
Requests / min30Nowhere near it — ~15 requests/run
Tokens / min12,000The binding constraint
Tokens / day100,000A run is ~40–70K, so ~1.5 runs/day

Divide it out: 30 RPM against 12K TPM allows an average of 400 tokens per request. A single agent turn carrying four tool results is far past that. The entire design is shaped by TPM and TPD; RPM never mattered.

Where do you put the rate limiter?

What they're testingWhether you've actually run a multi-agent system, or only read about one.

On a shared model client, not one per agent. LangChain's InMemoryRateLimiter paces per instance — give each of four subagents its own ChatGroq and you've quietly quadrupled your real rate while believing you're limited.

_SHARED: ChatGroq | None = None

def shared_llm() -> ChatGroq:
    """Process-wide singleton, so all agents share one bucket."""
    global _SHARED
    if _SHARED is None:
        _SHARED = build_llm()
    return _SHARED
Follow-up they will ask

"What breaks this?" — Horizontal scale. An in-memory bucket is per-process, so two workers means two buckets. Distributed rate limiting needs shared state: a Redis token bucket, or a proxy/gateway that owns the quota for everyone.

Token bucket, fixed window, or sliding window?

What they're testingStandard systems-design knowledge, applied rather than recited.
  • Fixed window — cheap, but allows a 2× burst across the boundary (all of minute 1's budget at :59, all of minute 2's at :01).
  • Sliding log — accurate, but stores a timestamp per request.
  • Token bucket — refills at a steady rate, allows a bounded burst up to bucket size. What LangChain implements. Ours uses max_bucket_size=3, so an agent that pauses to think can then fire three calls without being throttled.
  • Leaky bucket — strict smoothing, no burst allowed at all.
The real limitation

InMemoryRateLimiter is time-based only — it cannot see how many tokens a request carries, so a 10,000-token request and a 200-token request each consume exactly one bucket token. Against a TPM limit that's a blunt instrument. The actual defence is keeping payloads small at the source: our tools return formatted tables, not raw API responses. A raw get_metric_data reply is a few thousand tokens; the same information summarised is about thirty.

What happens when you run out of budget mid-run?

What they're testingGraceful degradation — whether you designed for the bad day.

Degrade in this order, and never skip to the last one:

  1. Truncate tool output harder.
  2. Lower AGENT_MAX_STEPS.
  3. Switch model — openai/gpt-oss-120b has 200K TPD versus llama-3.3-70b's 100K.
  4. Skip non-essential subagents.
  5. Emit a partial report saying what didn't run.

What you must never do is produce nothing. run_subagent() catches every exception and returns a degraded report, so a subagent that dies costs you one section — not the day's file. And a subagent that dies three days running becomes the finding.

Memory & context

Interviewers reach for "would you add a vector store?" Answer the question underneath it instead: what is the retrieval key, and does this system's data actually have a semantic one?

What kinds of memory does an agent have?

What they're testingVocabulary, then whether you can map it onto a real system.
  • Working / short-term — the message list inside one run. Bounded by the context window and, in practice, by cost long before that.
  • Long-term / persistent — anything surviving between runs. Needs a store and a retrieval key, and the key is the hard part.
  • Episodic (what happened), semantic (facts learned), procedural (how to do things — usually just the prompt).

Ours has working memory only. That's a deliberate choice, not an oversight, and the next question is where you defend it.

Your agent has no memory between runs. Defend that.

What they're testingWhether you can hold a position without being defensive, and concede a real cost.

Concede the cost first, because it's real and it's documented: a slow multi-week drift that never breaches a daily threshold on any single day is invisible to this agent. That's a genuine gap.

Then the defence:

  • The reports are the memory. reports/*.md is durable, human-readable, git-versioned and diffable. That is a better substrate for ops history than an embedding index, because a human can read it.
  • Ops data is a time series, so the retrieval key is time, not similarity. Semantic search over "cost was high on Tuesday" is the wrong tool for a question that is literally an ordered scan.
  • Therefore the right fix is deterministic: parse the last 7 reports' facts lists into a compact table and put it in the prompt. No embeddings, no retrieval failure modes, no new infrastructure.
Why this answer lands

It names the limitation before they do, explains the reasoning, and specifies the fix — while explaining why the fix they were fishing for (a vector store) would be the wrong one. That's a stronger signal than having built it.

How do you manage a context window that keeps growing?

What they're testingWhether you know the options and their failure modes, not just their names.
  • Trimming — keep the system prompt and the last k messages. Simple, and loses the middle.
  • Summarisation / compaction — compress old turns with a model call. The loss is silent, which is what makes it dangerous.
  • Truncate at the source — cap tool output before it ever enters the transcript. Cheapest and most predictable; this is what we do.
  • Context isolation — give each subagent its own clean window. This is multi-agent architecture's most underrated benefit: our cost agent never pays for the infrastructure agent's CloudWatch dumps.

Would you add a LangGraph checkpointer?

What they're testingWhether you add machinery reflexively or ask what it buys.

Answer the question with a question: what would I do with the checkpoint? Checkpointers buy two things — resumption after failure, and human-in-the-loop interrupt/resume. Resumption only matters when re-running is expensive.

This run takes five minutes and costs approximately nothing, and a daily batch job that either completes or re-runs from scratch is idempotent by construction. A checkpointer would add state to restore without adding capability.

When the answer flips

A long-running agent, an expensive tool with side effects partway through, or anything with a human approval step in the middle. Then SqliteSaver or a Postgres checkpointer keyed on thread_id earns its place immediately.

Tool calling

The mechanism is simple and worth being able to state precisely. The interesting decisions are all about what you put in a tool versus what you leave to the model.

How does tool calling actually work under the hood?

What they're testingThat you know the model never executes anything.
  1. Tool schemas — name, description, JSON Schema parameters — are serialised into the request alongside the messages.
  2. The model emits a structured tool_call block instead of text.
  3. Your runtime executes the function and appends the result as a tool message.
  4. The model is called again with the extended transcript. Loop until it returns a final answer or hits the step limit.

The implication people miss: the model selects a tool based on its description. Docstrings are prompt text, not documentation. Ours say when not to call — read_error_logs begins "Only call this after another tool has shown a non-zero error count," because it's the most token-expensive tool we have.

Why return errors as strings instead of raising?

What they're testingWhether you've debugged a real agent loop.

A raised exception kills the loop. A returned string is an observation the model can reason about and route around.

The refinement that matters more: distinguish error categories, because they mean different things about the world.

PrefixMeansCorrect agent response
TOOL_UNAVAILABLEIAM denied the callInfo finding about the agent's own role
TOOL_ERRORThe AWS call failedNote it, try another route
PROBLEMThe pipeline is genuinely brokenCritical or warning finding
Why the split earns its keep

Without it, a missing IAM permission gets reported as a production outage. That's a false critical — and once a human dismisses two of those, they stop reading the report, at which point the entire system is worse than nothing.

How many tools should one agent have?

What they're testingWhether your multi-agent split had a reason behind it.

Selection accuracy degrades as the tool list grows; on mid-size models the practical ceiling for reliable selection is roughly five to ten. That is a concrete argument for splitting: four agents at four to seven tools each beats one agent at eighteen.

Ours: infrastructure 7, cost 3, data quality 4, code 4.

How do you stop a tool being abused?

What they're testingDefence in depth versus a single clever guard.

Four layers, each assuming the ones above it failed:

  • Schema — parameter types constrain what can even be requested.
  • Application — the Athena tool rejects anything that isn't SELECT/WITH, rejects semicolons, rejects DDL keywords.
  • Filesystem — repo tools resolve paths and check is_relative_to(REPO_ROOT), with a deny-list covering .env, .git and the 300KB guide.
  • Infrastructure — a read-only IAM role carrying an explicit Deny on every mutating action.

The IAM deny is the one that holds when everything above it has been talked around, which is exactly the scenario the next question is about.

Where is your prompt injection exposure?

What they're testingWhether you can find the attack surface in your own system. Most candidates say "we don't take user input" and stop.

We do take untrusted input — it just doesn't look like it. The agent reads CloudWatch log lines, and those logs contain data derived from an external GTFS feed. Any text that reaches the logs reaches the model's context. That is a genuine injection channel.

The honest position: you cannot reliably prevent injection with prompting. So you constrain the blast radius instead. This agent has no write capability of any kind, so a successful injection produces at worst a wrong sentence in a report — not a dropped table, not a disabled alarm, not a pushed commit.

The line worth having ready

"An agent that cannot change anything is one you can afford to let be wrong." That single sentence is the justification for the whole read-only design, and it generalises well past this project.

Hallucination

"How do you stop hallucination?" is a trick question. You don't. You make hallucination structurally unable to matter, and you make it checkable after the fact.

How do you stop the agent hallucinating?

What they're testingWhether you reach for a silver bullet or a layered answer.

Reframe it first: you can't eliminate it, so constrain what it can do. Seven layers, roughly in order of how much they buy:

  • Grounding. Every finding must quote a number from a tool. The prompt is blunt about it: "If you did not call a tool for it, it is not a finding."
  • Determinism where it counts. Threshold comparisons and the month-end projection happen in Python. The prompt says "quote its numbers; do not recompute the projection yourself, you will get it wrong."
  • Structured output. A Pydantic schema via ToolStrategy means severity can't be a value outside the enum, and a finding can't arrive without a detail field.
  • Priors in the prompt. Measured baselines — 16M rows/day, ~$0.70/day, one ETL run at 02:20 UTC. Without them a model grades a normal day against a generic prior and reports it as alarming.
  • Verbatim carry-through. The supervisor copies findings rather than re-narrating them. A second model pass over the findings is a second opportunity to distort them.
  • Blast radius. Read-only, as above.
  • Auditability. The LangSmith trace lets a human walk any number in the report back to the tool call that produced it.

Doesn't temperature 0 fix this?

What they're testingA common misconception, stated confidently.

No. Temperature controls variance, not accuracy. A confidently wrong answer at temperature 0 is wrong reproducibly — arguably worse, since it looks stable. We run at 0.1 for consistent formatting, not for truthfulness.

Agents pad their output. How did you deal with that?

What they're testingWhether you've observed real model behaviour rather than assumed it.

Models treat an empty result as failing the task, so they manufacture findings to fill the list. Two fixes, and the second worked far better than the first:

  • Prompt: "An empty findings list with status healthy is the correct output on a good day and is what most days should produce."
  • Structure: the code agent is handed only the critical and warning findings — never the full healthy reports. Given three clean reports in full, it reliably found something to "improve."
The generalisable insight

Changing the input changed behaviour more than changing the instructions did. Prompt engineering is weaker than context engineering: if a model keeps doing something you told it not to, stop rewording and look at what you're feeding it.

How do you evaluate an agent like this?

What they're testingWhether "it seems to work" is your acceptance criterion.
  • Golden set from real incidents. This project has a gift here: twelve documented bugs and four cost overruns, with known-bad days. Replay those tool outputs as fixtures and assert the agent catches them.
  • Regression on frozen outputs. Pin a day's tool responses, assert the findings don't drift when the prompt changes.
  • Invariants, not exact text. Never assert on model prose. Assert "if dupes > 0 then a critical finding exists."
  • The deterministic layer, tested hard. --tools-only exercises every tool with no model at all. That's where the real bugs live.
  • Production signal. False-positive rate. If a human dismisses findings without acting, the agent is noise regardless of what any offline eval says.

Which failure mode worries you most?

What they're testingJudgement about asymmetric costs.

False negatives, by a wide margin. A false positive costs someone five minutes. A false negative means the pipeline was broken and the report said healthy — and now the report is actively worse than no report, because it manufactured confidence.

That asymmetry is written into the shared prompt: "Absence of a signal is worse than a failure signal." It's also why check_schedules exists — a paused EventBridge rule produces silence, not errors, so no error-based alarm will ever fire on it.

Multi-agent design

Multi-agent is fashionable, which means the interviewer is checking whether you chose it or defaulted to it.

Why four agents instead of one agent with eighteen tools?

What they're testingThat the split solved a problem you can name.
  • Tool selection accuracy degrades with tool count.
  • Context isolation — each subagent's window carries only its own tool output.
  • Independent failure — one agent dying costs one report section.
  • Different prompts encode genuinely different domain priors. "Normal" means something different to the cost agent than to the data quality agent.

And name the cost, because it isn't free: token multiplication (each agent pays for its own system prompt) plus orchestration complexity.

Supervisor routing or a fixed sequence — and why?

What they're testingWhether you spend LLM calls on decisions you already know the answer to.

Fixed sequence. The three specialists are independent and answer different questions, so there is nothing for a router to decide — an LLM router there could only introduce error. The code agent runs last because it genuinely depends on the others' output, and a dependency is expressible in code.

The principle generalises: don't spend a model call on a decision that isn't uncertain.

When routing is right

When the branch depends on content you can't predict — open-ended user requests, variable task types, an unknown number of steps. A fixed nightly job is the opposite of that.

How do subagents communicate?

What they're testingInterface design between non-deterministic components.

Structured Pydantic reports, not free text. Three reasons: the supervisor can count and sort findings without a model call; a schema costs a fraction of the tokens of a subagent narrating its work; and a contract fails loudly instead of silently.

Have the failure mode ready — the model sometimes answers in prose instead of calling the response tool, leaving structured_response as None. We keep the raw text, mark the report degraded, and carry on. Losing a run to a schema miss would be a worse outcome than an unstructured section.

Production & security

This is where a portfolio project either reads as a demo or as something that ran unattended and survived.

Why GitHub Actions rather than Lambda or ECS?

What they're testingWhether you weighed alternatives or picked the first thing that worked.
  • LangChain is roughly 40MB of transitive dependencies — awkward against Lambda's packaging limits, and a container image adds a build pipeline.
  • The deliverable is a markdown file that belongs in the repo. Actions commits it natively; Lambda would need a separate path back to git.
  • The code agent needs to open pull requests. Actions has a token for that; Lambda doesn't.
  • The OIDC provider already existed in the cicd module.
  • Free.

Name the trade-offs unprompted: scheduled runs are best-effort and GitHub delays them under load; scheduled workflows only fire from the default branch; and workflows are disabled after 60 days of repository inactivity — which this one solves incidentally by committing a report every day.

Walk me through least privilege here.

What they're testingWhether "read-only" is a claim or a policy document.
  • A separate role from the deploy role, which carries PowerUserAccess. Sharing it would have been one line of Terraform and a completely different risk profile.
  • Read-only grants, plus an explicit Deny statement covering every mutating action — so it holds even if someone later attaches a broader policy by mistake.
  • S3 scoped to project buckets. The one write in the whole policy is s3:PutObject on the Athena results prefix, because Athena cannot return a result without somewhere to write it.
  • OIDC federation — no long-lived access keys, one-hour sessions, trust policy scoped to a single repository.

How do you know the agent actually ran?

What they're testingWhether you apply your own monitoring standards to your monitoring.

Per run: a LangSmith trace, a committed report, an Actions step summary, and step outputs carrying the critical count. A missing file in reports/ is itself a signal.

Then concede the gap, because it's the same bug the agent hunts for in the ETL: nothing alerts when the workflow doesn't run at all. Failure alerts on failure, not on absence. The fix is a dead-man's-switch — a heartbeat that pages when it stops arriving.

Why volunteering this helps

It shows you apply the principle consistently rather than only where it was convenient. "Absence is silent" is in the agent's own prompt; noticing it applies to the agent too is the point.

How do you test a non-deterministic system in CI?

What they're testingPractical testing strategy under uncertainty.

Split the system at the determinism boundary and test each side differently. The tools are ordinary Python and deserve ordinary tests — mocked boto3, asserted output. That's where most bugs actually are. The model layer gets invariant assertions and frozen-fixture replay, never exact-text matching.

--tools-only exists precisely for this: it runs every tool against real AWS with no model in the loop, which also makes it the fastest way to find a missing IAM permission without spending a single token.

What does the agent cost to run?

What they're testingWhether you noticed the obvious trap in monitoring a cheap system.

Effectively zero: Groq free tier, Actions free on public repos at roughly five minutes a day, and AWS calls that are metric reads plus a handful of small Athena queries capped by the workgroup's byte limit.

State why that mattered: the pipeline being monitored costs $0.70/day. An observability layer costing more than the thing it observes is a bad trade, and on a project this size it would have been easy to build one.

Your weak points

Name these before the interviewer does. A candidate who volunteers the limitations of their own system reads as someone who has operated one; a candidate who defends everything reads as someone who hasn't.

No cross-run memory

A slow drift that never breaches a daily threshold is invisible. Fix is deterministic and cheap: load the last seven reports' facts into the prompt.

Nothing alerts on the agent's own absence

A workflow that never fires produces no failure. Needs a heartbeat that alerts on silence — exactly what the agent checks for in the ETL.

Prompt baselines go stale

The measured normals live in _SHARED_CONTEXT. Change the poll rate or add a feed and the agent grades against a world that no longer exists, silently.

The code agent is the weakest component

By construction — most of its proposals should be closed unreviewed. It cannot touch Terraform, IAM or the silver merge key at all. Worth saying plainly rather than overselling it.

The token budget is tight

~40–70K of a 100K daily allowance. A day with many findings, or a retry storm, could truncate the run. Mitigated by degradation, not eliminated.

No staging environment for the agent itself

Prompt changes go straight to the only environment there is. A frozen-fixture eval suite is the substitute, and it isn't built yet.
